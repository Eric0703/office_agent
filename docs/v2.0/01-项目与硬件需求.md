## 1. 项目定位与范围

**一句话定位**:AI 工牌是办公场景的 Agent 物理入口——它用「持续在身的身份展示与提醒」换取用户全天佩戴,用「明确的物理操作(按键)」换取可信的录音与指令触发,把重的识别、推理、系统操作留在个人电脑/企业内网完成。

**四条设计原则**(后续所有取舍的裁判标准):

1. **工牌只做感知和呈现,不做智能**。算力、电量、散热都不允许,也不应该。
2. **录音必须可感知、可追溯**。物理按键触发 + 录音指示灯常亮,是无感录音红线的前提。
3. **单一事实来源在受控环境**。记忆、任务状态、权限、凭据只存在于 PC/内网,佩戴设备丢失不泄露。
4. **先跑通闭环,再谈体验优化**。MVP 追求三个场景端到端可用,不追求单项体验极致。

**当前产品方向(Owner 决策,2026-07-22)**:硬件采用**方案 A 单屏 AI 工牌**——电子纸单屏承担身份展示与动态内容;已连接(含有待办)默认首页 = 员工身份信息(姓名/部门/二维码,不含配对码);页序:身份 → 待办/提醒卡 → 简报,上翻/下翻**双向循环**。整机**三枚物理键**:主操作键(录音/麦克风标识,按界面状态复用:录音开始/停止、候选选定/取消、L2 确认/取消、回身份首页)、上翻键、下翻键(键语义详见 09 §2);电子纸屏为纯显示区,无触摸按钮。方案 B(正面实体工卡 + 背面电子纸)仅作**备选方案**保留。凡涉及身份页与显示契约的条目以此为准。

## 2. Agent 架构决策:一个 Agent,两个进程

### 2.1 结论

**不要做两个 Agent。逻辑上只有一个 Agent,运行在 PC/企业内网侧;工牌端是一个"端侧代理运行时(Device Runtime)",它不是 Agent。**

| | 工牌端 Device Runtime | PC/内网端 Agent 核心 |
|---|---|---|
| 本质 | 能力受限的客户端 | 真正的 Agent(LLM 编排) |
| 职责 | 感知(录音、按键)、呈现(屏幕、LED、震动)、传输、极简状态机 | ASR、意图识别、推理、工具调用、记忆、权限与风险校验、内容生成 |
| 是否理解语义 | 否 | 是 |
| 是否持有凭据 | 否(只持有设备配对密钥) | 是(OA token、日历授权等) |
| 更新频率 | 低 | 高(周级甚至日级) |

### 2.2 为什么智能不能放工牌里

1. **能力错配**:佩戴设备对续航、重量、成本有硬上限,任何能跑有意义推理的算力都会击穿这些指标。
2. **状态一致性**:两个 Agent 各自持有记忆和任务状态必然引入同步冲突;单一事实来源必须只有一个。
3. **安全边界**:佩戴设备会丢。端侧只留配对密钥,丢失即吊销。
4. **迭代成本**:Agent 能力是迭代最频繁的部分,放在 PC 侧改完即生效;放固件里每次都要 OTA。

### 2.3 端侧需要"智能"的地方(不算 Agent)

以下能力属于**信号处理**,可以且应该放在端侧,不构成第二个 Agent:

- VAD(语音活动检测):判断说话结束,自动停止录音
- 断网录音缓存:音频先存本地,恢复连接后补传
- 录音的唯一触发方式是物理按键;不做任何声音/自动唤醒(红线见 §3.3)

### 2.4 业务流走向(数据视角)

```
[工牌] 按键/录音/屏幕/震动/LED
   │  音频上行、按键事件上行;简报、指令结果、确认请求下行
   ▼  传输通道(演示期 WebSocket/HTTP;硬件期 BLE/Wi-Fi/USB,协议语义不变,见 09)
[Agent 主机] 设备接入 → 核心流程(ASR → 置信度闸门 → 意图路由 → 权限/风险校验 → 技能执行)→ 结果回传
   ▼  适配层
[办公系统] 任务、日历、笔记/知识库(Mock 先行,真实系统经适配层替换)
```

要点:

- 工牌**永远不直接访问办公系统和公网**,所有外部调用都经过 Agent 核心的权限层。这是安全模型的根基。
- 演示期"PC 伴侣"与 Agent 核心合并为**单进程**(Agent 主机),降低部署与调试成本;硬件期如需拆分,进程边界不影响协议语义。

## 3. Agent MVP 功能列表

### 3.1 必须做(P0)

| # | 功能 | 理由 |
|---|---|---|
| 1 | 一键录音 + 录音中状态反馈(LED 常亮、震动、屏幕状态页) | 场景 1/3/4 的共同入口;物理按键 + 明确指示是合规与信任前提 |
| 2 | 音频与事件双向传输(配对绑定 + 加密) | 一切功能的管道;没有它工牌就是普通录音笔 |
| 3 | 断网录音本地缓存 + 恢复后补传 | 走廊、茶水间天然是弱网场景,不缓存就等于丢数据 |
| 4 | 身份展示(电子纸身份首页:姓名/部门/二维码,不含配对码)+ 动态内容页(待办/提醒卡、简报、结果) | 工牌的本职功能,是用户愿意全天佩戴的理由;方案 A 页序见 §1 |
| 5 | PC 端 ASR(语音转写) | 所有语音链路的第一个处理环节 |
| 6 | 意图路由(区分:现场记录/办公指令/经验沉淀) | 三类语音流入一个口,必须先分流再处理 |
| 7 | 现场录音 → 结构化笔记草稿(要点/结论/待办),人工确认后归档 | 场景 1 的核心价值;"人工确认后归档"是质量兜底 |
| 8 | 每日简报生成(拉取已授权的日历/任务,摘要生成)+ 同步工牌;工牌屏幕只承载待办任务与定时提醒两类卡片 | 场景 2 的核心价值,且是高频触点,养佩戴习惯;提醒范围收敛,不做通知中心 |
| 9 | 白名单任务指令执行("标记任务完成""查看今日日程"等);语音确认完成后,对应提醒即时从工牌屏幕撤下 | 场景 3 的最小验证;白名单控制爆炸半径;"说完即消"是提醒闭环的关键体验 |
| 10 | 风险确认回路(有影响的操作在工牌屏显示确认文案,实体键确认后执行) | 语音指令天然有误识别率,不可逆操作必须过确认 |
| 11 | 权限白名单 + 全量操作日志(谁、何时、说了什么、执行了什么、结果) | 企业场景的可审计性是准入门槛,不是加分项 |
| 12 | Agent 主机常驻(连接管理、配对/解绑、设备丢失吊销) | 安全模型和传输可靠性的载体 |

### 3.2 可以砍(P1/P2,有设计但不进 MVP)

| # | 功能 | 砍的理由与保留的口子 |
|---|---|---|
| 1 | 说话人分离与标注(diarization) | 初版用"说话人 1/2"粗分即可;走廊录音声学环境复杂,做好这个成本高 |
| 2 | TTS 语音播报 | 工牌反馈用屏幕+震动+LED 足够;扬声器徒增功耗、体积和办公环境打扰 |
| 3 | 专家经验 skill 自动化提取管线 | 场景 4 的 D2 子流程初期"人工触发 + 半自动 + 人工 review"即可,先验证经验资产有人用 |
| 4 | 面向用户的手机 App | PC 侧已覆盖配置与查看;工牌设计初衷就是减少看屏,不是再造一个屏(开发期的"虚拟工牌"演示端除外,见 02) |
| 5 | 网页管理后台 | 初期配置文件 + CLI 够用;试点阶段再做 |
| 6 | 加速度计/抬手刷新 | 电子纸常显不需要亮屏动作 |
| 7 | 三色电子纸(黑白红) | 刷新慢一倍;身份页的红字装饰价值不抵体验损失 |

### 3.3 明确不做(红线,任何阶段不碰)

| # | 事项 | 理由 |
|---|---|---|
| 1 | 持续环境监听 / 无感录音 | 隐私与合规红线;一旦被贴上"窃听工牌"标签,项目直接死亡 |
| 2 | 任何形式的自动/声音触发录音(唤醒词、环境音触发等) | 录音必须由人主动按键触发,规避审计、合规、伦理风险(用户决策) |
| 3 | IM 消息、邮件等通用通知推送到工牌 | 不做第二个智能手机/智能手表;工牌屏幕只承载待办任务与定时提醒(用户决策) |
| 4 | 工牌端 LLM 推理、工牌端对话式交互 | 见 §2.2;工牌是对讲机式的"按下说事",不是随身聊天机器人 |
| 5 | 摄像头及任何影像采集 | 录音已有明确按键与指示灯做合规锚点,影像没有等价的信任设计 |
| 6 | 工牌直连公网 / 直连办公系统 | 破坏"所有外部调用经 Agent 权限层"的安全模型 |
| 7 | 替代 OA/IM 的全功能客户端 | 工牌只做入口与状态呈现,重交互永远回到 PC |
| 8 | 录音文件的长期云端存储 | 音频是敏感资产,转写完成后默认删除原始音频(保留策略可配置,默认不留) |

## 4. 核心用户流程

### 4.0 角色与泳道定义

- **用户**:佩戴工牌的员工
- **工牌**:Device Runtime(感知/呈现/传输)
- **Agent 主机**:设备接入、识别/推理/权限/工具调用(单进程,含连接与协议层)
- **办公系统**:任务、日历、笔记/知识库

**录音触发统一约定(宪法第 2 条,v1.1)**:单键切换——按一下录音键开始,再按一下结束。以下场景不再分"长按/短按"。

### 4.1 场景一:捕捉并整理现场信息(走廊谈话 → 结构化笔记)

**前置**:工牌已与用户 PC 配对;用户在办公区内,PC 在线。

| 时序 | 泳道 | 动作 |
|---|---|---|
| T0 | 用户 | 走廊讨论中产生值得保留的观点,在端侧选择"现场记录"模式(或保持自动模式由主机路由;显式模式优先于自动路由,见 02 FR-04),**按一下录音键** |
| T1 | 工牌 | 震动一下,录音 LED 常亮,屏幕显示"录音中",开始录音 |
| T2 | 用户 | 正常交谈(近讲为主,环境音被收录但不保证质量) |
| T3 | 用户 | 谈完,**再按一下录音键**结束 |
| T4 | 工牌 | 震动两下,屏幕显示"上传中",音频发送;发送完成后 LED 熄灭 |
| T5 | Agent 主机 | 收齐音频,校验完整性 |
| T6 | Agent 主机 | ASR 转写 → LLM 结构化(背景/要点/结论/待办)→ 生成笔记草稿;**默认删除原始音频** |
| T7 | Agent 主机 | 桌面通知:"已生成《关于 XX 讨论》笔记草稿,请确认" |
| T8 | 用户 | 回到工位,查看草稿,编辑/确认 |
| T9 | Agent 主机 | 按用户确认结果:归档到笔记系统;识别出的待办转为任务草稿 |
| T10 | 工牌 | 下次同步时,提醒页出现"待确认任务 ×2" |

**完成态**:一条结构化笔记 + 0~N 条任务草稿,全程用户在工位外无需碰电脑。

**异常分支**:
- T4 时不在连接范围 → 端侧本地缓存,屏幕显示"已存本地,待同步",恢复后自动补传
- T6 转写质量差(信噪比过低)→ 草稿标注"转写置信度低",提示用户对照补录,不强行生成结论

### 4.2 场景二:日常办公(身份展示 + 每日简报)

| 时序 | 泳道 | 动作 |
|---|---|---|
| T0 | 用户 | 早上到岗,PC 开机,工牌在旁 |
| T1 | Agent 主机 | 检测到工牌连接,认证建立 |
| T2 | Agent 主机 | 拉取已授权的今日日历、任务列表,生成每日简报(3~5 条重点:今日会议、临期任务、冲突提醒) |
| T3 | Agent 主机 | 将简报页推送至工牌 |
| T4 | 工牌 | 默认首页显示员工身份(姓名/部门/二维码);待办/提醒卡(单卡一页,最高优先在前)与简报页由用户上翻/下翻双向循环查看(页面模型见 07 §6.1) |
| T5 | 用户 | 佩戴工牌外出开会/串门,身份首页持续展示身份;随时按键翻看今日重点 |
| T6 | Agent 主机 | 日间增量提醒仅限两类:待办任务(到期/催办)与定时提醒;推送到工牌,震动一下提示。不推送任何 IM、邮件、资讯类通知 |
| T7 | 用户 | 下班摘下工牌充电 |

**完成态**:用户全天未打开日历 App 也掌握了今日重点。

**异常分支**:
- T1 连接失败 → 工牌保持显示最后一次内容,角标提示"未同步",不阻塞身份展示
- T2 数据源无授权(如日历未接入)→ 简报只生成已有源,缺省项静默省略

### 4.3 场景三:语音执行办公任务(以"标记任务完成"为例)

| 时序 | 泳道 | 动作 |
|---|---|---|
| T0 | 用户 | **按一下录音键** |
| T1 | 工牌 | 震动,LED 亮,屏幕显示"录音中" |
| T2 | 用户 | 说:"把周报撰写任务标记为已完成",再按一下结束 |
| T3 | 工牌→Agent 主机 | 音频上行 |
| T4 | Agent 主机 | ASR → 意图识别:任务操作(完成);参数:任务名"周报撰写" |
| T5 | Agent 主机 | 权限与风险校验:该操作在白名单内、可逆 → 直接执行(若不可逆/影响他人 → 转 T5') |
| T6 | 办公系统 | 调用任务接口,标记完成 |
| T7 | Agent 主机→工牌 | 返回"已完成:周报撰写 ✓" |
| T8 | 工牌 | 震动 + 屏幕显示结果 3 秒;若该任务在提醒页有对应卡片,即时撤下("说完即消"),然后返回原页面 |

**确认分支 T5'**(高风险操作,如"把方案发给客户"):
- 工牌屏幕显示确认文案:"将向 客户A 发送《XX方案 v3》,长按主操作键执行"
- 用户**长按主操作键** → 确认,继续 T6;**短按主操作键**或 15 秒无操作 → 取消,工牌显示"已取消"

**异常分支**:
- 意图不清/参数缺失(同时存在两个"周报"任务)→ 不猜,工牌显示候选列表,用户按键选择
- 系统调用失败 → 工牌显示"失败:任务系统无响应,请稍后在电脑重试",日志留痕

### 4.4 场景四:专家经验沉淀

**D1 主动语音沉淀**(复用场景一链路,模板不同):

| 时序 | 动作 |
|---|---|
| T0 | 专家在端侧选择"经验记录"模式,按键口述项目复盘:"这次交付延期的根因是…下次应该…" |
| T1 | 与场景一 T4~T6 相同,结构化模板换成"场景/判断/依据/教训/可复用方法" |
| T2 | 生成经验卡片草稿,专家在 PC 端 review 确认 |
| T3 | 归档到该领域的经验库(skill 草稿) |

**D2 存量文档提取**(半自动,MVP 人工触发):

| 时序 | 动作 |
|---|---|
| T0 | 专家/管理员在 PC 端选中文档或邮件,触发"提取经验" |
| T1 | Agent 核心按模板抽取结构化经验,生成经验卡片草稿 |
| T2 | 人工 review、修订、确认 |
| T3 | 入库,沉淀为该领域的专家 skill;后续 Agent 处理同类问题时自动引用 |

**关键设计**:MVP 不追求自动化提取管线,先验证"经验卡片有人产、有人用"。D1/D2 产出**必须经人工确认才能入库**——经验库的错误内容比普通笔记危害大得多。

### 4.5 通用异常(全场景适用)

- **设备未配对/被吊销**:工牌仅显示"请重新配对",录音键无效
- **PC 离线**:录音本地缓存;指令类操作直接提示"电脑不在线,无法执行"
- **连续误触发**:录音 <2 秒视为误触,不上传不提醒,静默丢弃

## 5. 硬件目标与约束

> **边界声明**:实体硬件**未进入开发**。本章只保留目标与约束级结论,作为未来硬件接入的输入;选型、BOM、结构、射频等工程细节属历史参考(docs/ 根旧文档),不作为当前开发依据。硬件接入时必须保持的软件接口边界见 `09-设备能力与硬件接入规范.md`。

### 5.1 两方案定位

| | 方案 A:独立式 AI 工牌(**当前产品方向**) | 方案 B:组合式智能工卡套(备选方案) |
|---|---|---|
| 定位 | 不依赖现有工卡的独立智能工牌 | 不替代现有工卡:实体工卡负责身份与门禁,卡套/背夹承担录音与动态内容显示 |
| 身份/门禁 | 电子纸身份首页(姓名/部门/二维码);门禁需 NFC 另行立项 | 现有工卡原生保留;需通过门禁抗干扰实测 |
| 显示分工 | 电子纸单屏承担身份页 + 动态内容(页序:身份 → 待办/提醒卡 → 简报,双向循环) | 实体工卡 = 身份(姓名/部门/二维码);电子纸 = 动态内容(提醒/简报/结果) |
| 主要风险 | 自研链路(功耗/重量/射频)、NFC 门禁前置条件 | 录音卡接口开放度、门禁干扰、结构遮挡 |

### 5.2 设计约束(从业务场景反推)

| 约束 | 来源 |
|---|---|
| 全天佩戴,重量与厚度有硬上限 | 用户愿意戴是前提,重了先摘的就是它 |
| 屏幕常显、无背光焦虑 | 身份/待办展示要求「一直亮着」,只有电子纸满足且静态零功耗 |
| 录音功耗不拖垮续航 | 录音+传输是耗电大头,决定电池容量 |
| 录音行为可感知 | 合规:LED 必须与录音硬件联动,软件不可旁路 |
| 成本可控(小批量试点量级) | 试点不能是奢侈品 |
| 企业数据主权 | 音频与待办数据不进入未经授权的第三方云端;原始音频转写后默认删除;设备丢失可一键吊销 |
| 不破坏现有门禁 | 员工不能因戴新设备刷不开门 |

### 5.3 硬件红线(任何样机阶段不得豁免)

- **录音 LED 硬件联动**:录音指示灯的供电与麦克风供电联动,固件无法单独旁路;物理按键是触发录音使能的唯一途径;<2 秒录音静默丢弃作为软件兜底。
- **禁止声控录音**:选用的任何成品录音模块若带「声控录音」功能,必须固件/设置层面禁用并写入验收 checklist。
- **不拆改成品录音模块内部电源**(安全与保修红线)。
- **门禁能力不承诺**:不得声称「加 NFC 芯片即可刷企业门禁」;门禁能力依赖门禁系统类型、发卡权限与密钥托管,必须显式立项确认。
- **开发验证件与量产件分离**:开发板/带排针模块只用于验证,不得出现在工程样机中。

### 5.4 验收门槛(硬件阶段的 Go/No-Go 量化标准,目标级)

| 标准 | 门槛 |
|---|---|
| 音频自动进入 Agent 主机 | 无需人工干预,传输成功率 ≥99% |
| 门禁(仅方案 B 备选启用时) | 读卡距离 ≥ 现有工卡裸卡的 80%(逐级实测) |
| 录音键/LED/声孔 | 结构零遮挡,LED 各角度可见 |
| 待办刷新成功率 | ≥99%(含断连重传) |
| 续航 | 满足全天佩戴目标(以实测功耗模型为准) |
| 数据主权 | 音频不进入未经授权的第三方云 |

## 7. 关键假设与待决问题

以下问题不阻塞软件开发,但影响企业化阶段设计:

1. **办公系统 API 可用性**:任务/日历系统是否开放接口、认证方式如何?决定场景 2/3 的可行边界。
2. **LLM 部署形态**:企业内网大模型 API、PC 本地模型,还是混合?影响 ASR/结构化的时延与数据出域策略。
3. **Agent 主机的安装权限**:企业 IT 策略是否允许常驻程序?需要提前与 IT 对齐。
4. **录音合规口径**:公司制度对"按键录音 + LED 指示"是否足够,还是被录音方需额外告知?建议法务早介入。
5. **工牌丢失的 HR/IT 流程**:吊销、补办、原设备数据责任的归属流程,试点前需成文。
6. **门禁系统类型与发卡权限**:现有工卡是 13.56MHz 还是 125kHz?是否允许第二凭证?决定方案 B 的干扰测试方法。

实现层面的未决问题(FR 缺口、体验待办)集中登记于 `README.md` §5 未决问题清单。
