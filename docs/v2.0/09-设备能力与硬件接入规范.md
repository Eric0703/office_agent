## 1. Device Capabilities(设备能力自报)

### 1.1 总则

- `device.hello` payload 新增**可选**字段 `capabilities`(08 §2.1),向后兼容:缺失等价于能力未知,不影响连接与既有功能。
- **主机只登记不消费、不落库**;未知子字段必须被忽略(前向兼容,规约 §3)。
- **`display_profile` 保留,仍是渲染档位的唯一权威**;`capabilities.screen` 不参与档位判定。
- **生命周期绑定当前连接**:每次 hello 必替换能力快照(携带 → 替换;未携带 → 清除旧值,能力未知);`push`/`broadcast` 发现当前登记连接失效时同步清理;旧连接迟到退出(身份守卫)不得清新连接的能力(07 §2.1)。

### 1.2 字段定义

`capabilities` 为 object,全部子字段可选;语义为设备能力自报,主机当前不消费,未来消费规则另行登记。

| 子字段 | 类型 | 说明 |
|---|---|---|
| `audio` | object | 音频能力:`formats` string[](可编码/上传格式,如 `["opus","wav"]`);`sample_rate` int(采样率,如 16000);`channels` int(声道数,如 1) |
| `screen` | object | 屏幕:`type` string(`"eink"` / `"lcd"` / `"none"`);`width` / `height` int(像素;虚拟工牌报仿真画布 300×400 竖向,实体模组报物理参数);`profile` string(同 display_profile 档位:`400x300` / `296x128`) |
| `keys` | string[] | 设备具备的物理键, ⊆ `["action","page_up","page_down"]`(§2) |
| `led` | bool | 是否有录音指示 LED |
| `haptics` | bool | 是否有震动反馈 |
| `storage_mb` | int | 离线缓存容量(MB) |
| `battery` | bool | 是否电池供电 |
| `network` | string[] | 网络能力,如 `["wifi","ble","usb"]` |
| `firmware_version` | string | 固件版本 |

### 1.3 示例

虚拟工牌(PWA)的实际上报(实现:`frontend/src/lib/ws-client.ts`),与方案 A 一致——单屏电子纸 + 三枚物理键(主操作键/上翻/下翻);`firmware_version` 对 PWA 无意义,不上报:

```json
{
  "type": "device.hello",
  "version": "1.0",
  "id": "3f6b2c1e-0000-4000-8000-000000000001",
  "ts": 1784800000000,
  "payload": {
    "device_id": "dev-a1b2c3d4e5f6",
    "token": "<配对 token>",
    "client": "vbadge-web",
    "client_version": "0.1.0",
    "display_profile": "400x300",
    "capabilities": {
      "audio": { "formats": ["webm-opus"], "channels": 1 },
      "screen": { "type": "eink", "width": 300, "height": 400, "profile": "400x300" },
      "keys": ["action", "page_up", "page_down"],
      "led": true,
      "haptics": true,
      "network": ["wifi"]
    }
  }
}
```

说明:`screen.width/height` 为仿真画布逻辑像素(300×400 竖向,07 §6.3),`profile` 随端侧档位上报(`400x300` / `296x128`);实际上报的端到端断言见 `frontend/e2e/badge-keys.spec.ts`。

## 2. 统一设备输入语义(三层模型)

### 2.1 三层区分

设备输入严格分三层,不得混用:

| 层 | 内容 | 说明 |
|---|---|---|
| **物理键**(3 枚) | `action` 主操作键(实体为录音/麦克风标识) / `page_up` 上翻 / `page_down` 下翻 | 实体 GPIO 键或 PWA 虚拟物理键(电子纸画布外);键名即 `capabilities.keys` 自报值(§1);**第四枚"确认·返回"键已删除,不得恢复** |
| **手势**(2 种) | 短按(默认)/ 长按(≥600ms,端侧计时) | 手势是键语义的一部分,不是独立键;仅 `action` 区分长按,其余键长按 no-op;**双击只预留、不实现,单击响应零延迟** |
| **内部语义动作** | `toggleRecording` / 翻页 `page±1` / `pick` / `cancelClarify` / `respond` / `dismissResult` / 回身份首页 | 端侧动作函数,按"物理键 × 手势 × 当前状态"分派;协议消息不变(record.start/stop、confirm.response、clarify.select) |

### 2.2 主操作键按界面状态复用(键 × 手势 × 状态 → 语义动作)

| 物理键 | 手势 | 界面状态 | 语义动作 |
|---|---|---|---|
| `action` | 短按 | 普通页面(身份/卡片/简报) | 开始录音(record.start) |
| `action` | 短按 | 录音中 | 结束并上传(record.stop + audio.upload) |
| `action` | 短按 | clarify 候选页 | `pick` 选定当前高亮候选(手机档多任务预览 = 全部创建,带 edited_labels) |
| `action` | 短按 | 失败/未听清结果页 | `dismissResult` 关闭结果 |
| `action` | 短按 | L2 确认页(confirm_wait) | `respond(cancel)` **取消** |
| `action` | 长按 | clarify 候选页 | `cancelClarify` 取消并退出(任务类发 `task:cancel`,提醒类发 `remind:cancel`,按候选前缀选择;服务端回终态"已取消",08 §2.3;手机档多任务预览 = 取消预览) |
| `action` | 长按 | L2 确认页(confirm_wait) | `respond(confirm)` **确认执行** |
| `action` | 长按 | 失败/未听清结果页 | 关闭结果并回身份首页(页 0) |
| `action` | 长按 | 录音中 | no-op |
| `action` | 长按 | 其余普通页面 | 回身份首页(页 0) |
| `page_up` / `page_down` | 短按 | 任意 | clarify 展示中:高亮 ±1 **双向循环**移动;否则页模型翻页 ±1(身份首页 → 待办/提醒卡 → 简报,双向循环,07 §6.1) |
| `page_up` / `page_down` | 长按 | 任意 | no-op |

### 2.3 唯一入口约定

- PWA 以 `pressKey(key, gesture)` 为**唯一输入语义入口**(`key ∈ action|page_up|page_down`,`gesture ∈ short|long`;实现:`frontend/src/lib/device-input.ts`);虚拟物理键(电子纸画布外 `.hw-keys`,主操作键经 pointer 事件按 600ms 计时区分长按)与手机演示按钮同走此接口。
- **按键处理在端侧,协议消息不变**(record.start/stop、confirm.response、clarify.select);状态机与业务**不区分事件来源**。
- 电子纸屏幕为纯显示区:卡片/简报/录音状态/候选/确认/结果;**屏幕内不出现"开始录音/点击结束"触摸按钮**(07 §6.4);clarify 候选在电子纸档纯展示 + 高亮,移动/选定/取消全部由物理键完成。
- **clarify 取消是完整服务端终态**:长按主操作键发 `task:cancel`(任务类,歧义与多任务预览通用)或 `remind:cancel`(提醒类);服务端不执行任何候选,records 落终态、审计记 `cancelled`、回终态 `intent.result`(status=success,"已取消")——离线音频凭据可出队,断线重连与 duplicate 恢复重放终态,不会回到候选页(07 §2.1、08 §2.3)。

### 2.4 GPIO 映射约定(硬件期)

- 实体 GPIO 按键由固件映射到同一物理键集:**实体键 + 短/长按手势 → 同一语义动作**(§2.2);映射表由固件侧固定,主机不感知物理键位;长按阈值(≥600ms)由端侧计时。
- 设备具备的物理键经 `capabilities.keys` 自报(§1);缺失某键(如无 `page_up`/`page_down`)时,对应功能在端侧降级(如简报不可翻页),协议与主机行为不变。
- 新增手势(如组合键)如需引入,先在端侧映射为现有键 × 手势;物理键集本身不变更——确需扩展时走协议治理(规约 §3)。

## 3. Transport 接口契约

### 3.1 定位

`gateway/transport` 定义传输抽象,是 `gateway/manager` 与具体通道之间的唯一触点;`gateway/manager` 只管设备身份/配对/会话/状态同步/协议语义,**不碰传输 API**。WebSocketTransport 为当前唯一实现;未来 BLE/Wi-Fi/USB 实现同一接口,协议消息零变更(宪法第 6 条)。

落位:`Transport` 抽象(Protocol)与 `WebSocketTransport` 实现位于 `gateway/transport.py`;`gateway/manager.py` 只依赖 Transport 抽象;断开异常统一为 `TransportClosed`(§3.3)。

### 3.2 接口方法

| 方法 | 语义 |
|---|---|
| `accept()` | 建立/接受一条连接(服务端侧等待对端接入完成) |
| `receive_text() -> str` | 接收一条文本消息(控制通道为 JSON 信封字符串);对端断开时抛出断开异常(§3.3) |
| `send_text(data: str)` | 发送一条文本消息(序列化后的 JSON 信封) |
| `close()` | 关闭连接;幂等,重复调用不报错 |

### 3.3 异常与协程约定(照当前代码写实)

- **全部为 asyncio 协程**,无多线程共享;连接对象归属其接收协程:`manager.handle_connection` 驱动 `receive_text` 循环,`send_text` 由 manager 在应答/推送路径(`push`/`broadcast`/hello 与配对响应)调用。
- **断开语义**:接收侧对端断开以异常表达——Transport 抽象定义统一的断开异常 `TransportClosed`,各实现负责把底层断开映射到该异常(`WebSocketTransport` 捕获 `fastapi.WebSocketDisconnect` 并转换,receive/send 两侧均覆盖);manager 只捕获 `TransportClosed` 做清理(连接注销、配对挂起态回收);同 `device_id` 重连后,旧连接迟到退出经身份守卫,不清新连接登记与 capabilities(07 §2.1)。
- **发送失败容错**:`push`/`broadcast` 捕获 `TransportClosed` 后记日志、**按离线跳过**(若失效连接仍是该设备的登记连接则移除,后续推送走离线路径,恢复经 `state.sync`,08 §2.6);`broadcast` 中单条假死连接不影响其余设备投递。投递失败不影响终态落库、结果缓存(duplicate 补推)与审计(07 §2.1);请求/应答路径(hello.result/pair.result/ack/pong)异常语义不变。
- 音频通道不经 Transport:HTTP POST `/audio/{record_id}` 独立于控制通道(08 §1.1)。

## 4. 硬件接入:做什么 / 不做什么

### 4.1 做什么(当前)

- 传输:WebSocket 控制通道 + HTTP 音频上传(局域网);WebSocketTransport 为唯一 Transport 实现。
- 接入:配对(6 位码 + Owner 批准)、hello 认证、吊销;capabilities 接收登记(只登记不消费)。
- 输入:三层输入语义约定(物理键 × 手势 → 语义动作,§2),虚拟工牌与未来实体工牌共用。
- 分层定界:Agent API(`/desk/*`、`/audio` 等)面向 PC、CLI 与未来软件集成;设备协议(WS)只管虚拟/实体工牌的事件、状态与结果展示。

### 4.2 不做什么(当前阶段明确不做)

| 事项 | 说明 |
|---|---|
| MQTT | 当前不引入;设备协议就是本登记册的 WS 语义,不加第二套消息通道 |
| BLE 实现 | 不实现;BLE 映射设计属 A3 按需项(未启动,见 v2.0 README §5) |
| OTA | 不做固件空中升级机制(实体硬件未进入开发,01 §5) |
| NFC | 不做;门禁能力显式立项前不承诺(01 §5.3 硬件红线) |
| 量产计划 | 不做选型/BOM/结构/排期(01 §5 边界声明) |
| 端侧智能 | 端侧不做语义理解、不持有办公系统凭据(宪法第 1 条) |

## 5. 实体工牌与虚拟工牌的等价性约定

**协议语义不变,只换传输。** 实体工牌接入时,以下逐项等价:

| 维度 | 约定 |
|---|---|
| 协议消息 | 同一登记册(08):同一信封、同一消息集、同一错误码;硬件期仅将控制通道映射到新 Transport 实现 |
| 状态机语义 | 端侧运行时状态机(07 §1.1)语义共用;固件按同一状态语义实现 |
| 键语义 | 实体 GPIO 键 + 短/长按手势映射到 action/page_up/page_down 的语义动作(§2);按键处理在端侧 |
| 显示档位 | `display_profile` 声明与主机截断规则不变;capabilities.screen 只登记(§1.1) |
| 认证配对 | 同一配对流程(6 位码 + Owner 批准 + token);设备即身份 |
| 测试复用 | 协议级测试套件(A1-7 无头客户端)对新 Transport 实现直接复用(05 §5 A3-1 验收) |

虚拟工牌在硬件接入后降级为测试工具,协议级回归持续有效。
