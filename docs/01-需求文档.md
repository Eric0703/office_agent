## 1. 项目定位与范围

**一句话定位**: AI 工牌是办公场景的 Agent 物理入口——它用「持续在身的身份展示与提醒」换取用户全天佩戴,用「明确的物理操作(按键)」换取可信的录音与指令触发,把重的识别、推理、系统操作留在个人电脑/企业内网完成。

**四条设计原则**(后续所有取舍的裁判标准):

1. **工牌只做感知和呈现,不做智能**。算力、电量、散热都不允许,也不应该。
2. **录音必须可感知、可追溯**。物理按键触发 + 录音指示灯常亮,是无感录音红线的前提。
3. **单一事实来源在受控环境**。记忆、任务状态、权限、凭据只存在于 PC/内网,佩戴设备丢失不泄露。
4. **先跑通闭环,再谈体验优化**。MVP 追求三个场景端到端可用,不追求单项体验极致。

## 2. Agent 架构决策: 一个 Agent,两个进程

### 2.1 结论(回答"是不是要做两个 Agent")

**不要做两个 Agent。逻辑上只有一个 Agent,运行在 PC/企业内网侧;工牌端是一个"端侧代理运行时(Device Runtime)",它不是 Agent。**

物理上确实有两个进程在跑,但二者性质完全不同:

| | 工牌端 Device Runtime | PC/内网端 Agent 核心 |
|---|---|---|
| 本质 | 能力受限的客户端(固件) | 真正的 Agent(LLM 编排) |
| 职责 | 感知(录音、按键)、呈现(屏幕、LED、震动)、传输、极简状态机 | ASR、意图识别、推理、工具调用、记忆、权限与风险校验、内容生成 |
| 是否理解语义 | 否 | 是 |
| 是否持有凭据 | 否(只持有设备配对密钥) | 是(OA token、日历授权等) |
| 更新频率 | 低(OTA,季度级) | 高(周级甚至日级) |

### 2.2 为什么智能不能放工牌里

1. **能力错配**:工牌目标续航 5 个工作日、重量 <60g、BOM ~¥120。任何能跑有意义推理的算力都会立刻击穿这三个指标。
2. **状态一致性**:如果两个 Agent 各自持有记忆和任务状态,必然引入同步冲突("工牌说完成了,电脑说没有")。单一事实来源必须只有一个。
3. **安全边界**:佩戴设备会丢。办公系统凭据、用户数据落在工牌上,丢一个工牌就是一次安全事故。端侧只留配对密钥,丢失即吊销。
4. **迭代成本**:Agent 能力是本项目迭代最频繁的部分,放在 PC 侧改完即生效;放固件里每次都要 OTA,还要考虑升级失败变砖。

### 2.3 端侧需要"智能"的地方(不算 Agent)

以下能力属于**信号处理**,可以且应该放在端侧,不构成第二个 Agent:

- VAD(语音活动检测):判断说话结束,自动停止录音
- 断网录音缓存:音频先存本地 Flash,恢复连接后补传
- 录音的唯一触发方式是物理按键;不做任何声音/自动唤醒(用户决策,红线见 §3.3)

### 2.4 业务流走向(数据视角)

```
[工牌] 按键/录音/屏幕/震动/LED
   │  音频上行、按键事件上行;简报、指令结果、确认请求下行
   ▼  BLE(信令/小数据,常连)+ Wi-Fi(音频大文件,按需唤起)+ USB(配对/调试/兜底)
[PC 伴侣程序] 常驻托盘,负责连接管理、设备配对、断点补传、协议封解
   ▼  本地进程间调用(MVP 阶段与 Agent 核心同一进程,后续可拆)
[Agent 核心] ASR → 意图路由 → 权限/风险校验 → 工具调用/内容生成 → 结果回传
   ▼  企业内网授权接口
[办公系统] 任务、日历、笔记/知识库、邮件
```

要点:工牌**永远不直接访问办公系统和公网**,所有外部调用都经过 Agent 核心的权限层。这是安全模型的根基。

## 3. Agent MVP 功能列表

### 3.1 必须做(P0)

| # | 功能 | 理由 |
|---|---|---|
| 1 | 一键录音 + 录音中状态反馈(LED 常亮、震动、屏幕计时) | 场景 1/3/4 的共同入口;物理按键 + 明确指示是合规与信任前提 |
| 2 | 音频与事件双向传输(配对绑定 + 加密,BLE 信令 + Wi-Fi 传音频) | 一切功能的管道;没有它工牌就是普通录音笔 |
| 3 | 断网录音本地缓存 + 恢复后补传 | 走廊、茶水间天然是弱网场景,不缓存就等于丢数据 |
| 4 | E-ink 身份页(姓名/部门/二维码)+ 简报/提醒页显示 | 工牌的本职功能,是用户愿意全天佩戴的理由 |
| 5 | PC 端 ASR(语音转写) | 所有语音链路的第一个处理环节 |
| 6 | 意图路由(区分:现场记录/办公指令/经验沉淀) | 三类语音流入一个口,必须先分流再处理 |
| 7 | 现场录音 → 结构化笔记草稿(要点/结论/待办),人工确认后归档 | 场景 1 的核心价值;"人工确认后归档"是质量兜底 |
| 8 | 每日简报生成(拉取已授权的日历/任务,摘要生成)+ 同步工牌;工牌屏幕只承载待办任务与定时提醒两类卡片 | 场景 2 的核心价值,且是高频触点,养佩戴习惯;提醒范围收敛,不做通知中心 |
| 9 | 白名单任务指令执行(2~3 个高频指令,如"标记任务完成""查看今日日程");语音确认完成后,对应提醒即时从工牌屏幕撤下 | 场景 3 的最小验证;白名单控制爆炸半径;"说完即消"是提醒闭环的关键体验 |
| 10 | 风险确认回路(有影响的操作在工牌屏显示确认文案,实体键确认后执行) | 语音指令天然有误识别率,不可逆操作必须过确认 |
| 11 | 权限白名单 + 全量操作日志(谁、何时、说了什么、执行了什么、结果) | 企业场景的可审计性是准入门槛,不是加分项 |
| 12 | PC 伴侣程序(常驻、连接管理、配对/解绑、设备丢失吊销) | 安全模型和传输可靠性的载体 |

### 3.2 可以砍(P1/P2,有设计但不进 MVP)

| # | 功能 | 砍的理由与保留的口子 |
|---|---|---|
| 1 | 说话人分离与标注(diarization) | 初版用"说话人 1/2"粗分即可;走廊录音声学环境复杂,做好这个成本高 |
| 2 | TTS 语音播报 | 工牌反馈用屏幕+震动+LED 足够;扬声器徒增功耗、体积和办公环境打扰 |
| 3 | 专家经验 skill 自动化提取管线 | 场景 4 的 D2 子流程初期"人工触发 + 半自动 + 人工 review"即可,先验证经验资产有人用 |
| 4 | 面向用户的手机 App | PC 伴侣已覆盖配置与查看;工牌设计初衷就是减少看屏,不是再造一个屏(开发期的"虚拟工牌"演示端除外,见 02 文档) |
| 5 | 网页管理后台 | 初期配置文件 + CLI 够用;试点阶段(50+ 设备)再做 |
| 6 | 加速度计/抬手刷新 | 电子纸常显不需要亮屏动作;只影响按键寿命优化,PCB 预留焊盘 |
| 7 | 磁吸/无线充电 | USB-C 成本低、可靠性高;充电触点增加结构与防水难度 |
| 8 | 三色电子纸(黑白红) | 刷新慢一倍;身份页的红字装饰价值不抵体验损失,结构件上做品牌色更划算 |

### 3.3 明确不做(红线,任何阶段不碰)

| # | 事项 | 理由 |
|---|---|---|
| 1 | 持续环境监听 / 无感录音 | 隐私与合规红线;一旦被贴上"窃听工牌"标签,项目直接死亡 |
| 2 | 任何形式的自动/声音触发录音(唤醒词、环境音触发等) | 录音必须由人主动按键触发,规避审计、合规、伦理风险(用户决策) |
| 3 | IM 消息、邮件等通用通知推送到工牌 | 不做第二个智能手机/智能手表;工牌屏幕只承载待办任务与定时提醒(用户决策) |
| 4 | 工牌端 LLM 推理、工牌端对话式交互 | 见 §2.2;工牌是对讲机式的"按下说事",不是随身聊天机器人 |
| 5 | 摄像头及任何影像采集 | 录音已有明确按键与指示灯做合规锚点,影像没有等价的信任设计 |
| 6 | 工牌直连公网 / 直连办公系统 | 破坏"所有外部调用经 Agent 权限层"的安全模型 |
| 7 | 替代 OA/IM 的全功能客户端 | 工牌只做入口与状态呈现,重交互永远回到 PC |
| 8 | 录音文件的长期云端存储 | 音频是敏感资产,转写完成后默认删除原始音频(保留策略可配置,默认不留) |

## 4. 核心用户流程

### 4.0 角色与泳道定义

- **用户**:佩戴工牌的员工
- **工牌**:Device Runtime(感知/呈现/传输)
- **PC 伴侣**:连接与协议层(可与 Agent 核心同进程)
- **Agent 核心**:识别/推理/权限/工具调用
- **办公系统**:任务、日历、笔记/知识库

### 4.1 场景一:捕捉并整理现场信息(走廊谈话 → 结构化笔记)

**前置**:工牌已与用户 PC 配对;用户在办公区内,PC 在线。

| 时序 | 泳道 | 动作 |
|---|---|---|
| T0 | 用户 | 走廊讨论中产生值得保留的观点,**长按录音键**进入"现场记录"模式(与"预切模式后按键"等价,二选一;显式模式优先于自动路由,见 02 FR-04) |
| T1 | 工牌 | 震动一下,录音 LED 常亮,屏幕显示"记录中 00:01…",开始录音 |
| T2 | 用户 | 正常交谈(近讲为主,环境音被收录但不保证质量) |
| T3 | 用户 | 谈完,**再按一次录音键**结束 |
| T4 | 工牌 | 震动两下,屏幕显示"上传中",音频分片经 Wi-Fi 发送;发送完成后 LED 熄灭 |
| T5 | PC 伴侣 | 收齐音频,校验完整性,转交 Agent 核心 |
| T6 | Agent 核心 | ASR 转写 → LLM 结构化(背景/要点/结论/待办)→ 生成笔记草稿;**默认删除原始音频** |
| T7 | PC 伴侣 | 桌面通知:"已生成《关于 XX 讨论》笔记草稿,请确认" |
| T8 | 用户 | 回到工位,查看草稿,编辑/确认 |
| T9 | Agent 核心 | 按用户确认结果:归档到笔记系统;识别出的待办转为任务草稿 |
| T10 | 工牌 | 下次同步时,提醒页出现"待确认任务 ×2" |

**完成态**:一条结构化笔记 + 0~N 条任务草稿,全程用户在工位外无需碰电脑。

**异常分支**:
- T4 时不在 Wi-Fi/PC 范围 → 工牌本地缓存,屏幕显示"已存本地,待同步",恢复后自动补传
- T6 转写质量差(信噪比过低)→ 草稿标注"转写置信度低",提示用户对照补录,不强行生成结论

### 4.2 场景二:日常办公(身份展示 + 每日简报)

| 时序 | 泳道 | 动作 |
|---|---|---|
| T0 | 用户 | 早上到岗,PC 开机,工牌在旁 |
| T1 | PC 伴侣 | 检测到工牌 BLE 广播,建立加密连接 |
| T2 | Agent 核心 | 拉取已授权的今日日历、任务列表,生成每日简报(3~5 条重点:今日会议、临期任务、冲突提醒) |
| T3 | PC 伴侣 | 将简报页推送至工牌 |
| T4 | 工牌 | 屏幕刷新:身份页(常态)→ 简报页(用户按键切换查看) |
| T5 | 用户 | 佩戴工牌外出开会/串门,工牌持续展示身份;随时按键翻看今日重点 |
| T6 | Agent 核心 | 日间增量提醒仅限两类:待办任务(到期/催办)与定时提醒;推送到工牌,震动一下提示。不推送任何 IM、邮件、资讯类通知 |
| T7 | 用户 | 下班摘下工牌,放充电座/插 USB-C |

**完成态**:用户全天未打开日历 App 也掌握了今日重点。

**异常分支**:
- T1 连接失败 → 工牌保持显示最后一次简报,角标提示"未同步",不阻塞身份展示
- T2 数据源无授权(如日历未接入)→ 简报只生成已有源,缺省项静默省略

### 4.3 场景三:语音执行办公任务(以"标记任务完成"为例)

| 时序 | 泳道 | 动作 |
|---|---|---|
| T0 | 用户 | **短按录音键** |
| T1 | 工牌 | 震动,LED 亮,屏幕显示"请讲" |
| T2 | 用户 | 说:"把周报撰写任务标记为已完成"(松开发送) |
| T3 | 工牌→PC 伴侣 | 音频上行 |
| T4 | Agent 核心 | ASR → 意图识别:任务操作(完成);参数:任务名"周报撰写" |
| T5 | Agent 核心 | 权限与风险校验:该操作在白名单内、可逆 → 直接执行(若不可逆/影响他人 → 转 T5') |
| T6 | 办公系统 | 调用任务接口,标记完成 |
| T7 | Agent 核心→工牌 | 返回"已完成:周报撰写 ✓" |
| T8 | 工牌 | 震动 + 屏幕显示结果 3 秒;若该任务在提醒页有对应卡片,即时撤下("说完即消"),然后回到身份页 |

**确认分支 T5'**(高风险操作,如"把方案发给客户"):
- 工牌屏幕显示确认文案:"将向 客户A 发送《XX方案 v3》,按确认键执行"
- 用户按**确认键** → 继续 T6;按**返回键**或 15 秒无操作 → 取消,工牌显示"已取消"

**异常分支**:
- 意图不清/参数缺失(同时存在两个"周报"任务)→ 不猜,工牌显示候选列表,用户按键选择
- 系统调用失败 → 工牌显示"失败:任务系统无响应,请稍后在电脑重试",日志留痕

### 4.4 场景四:专家经验沉淀

**D1 主动语音沉淀**(复用场景一链路,模板不同):

| 时序 | 动作 |
|---|---|
| T0 | 专家在工牌上选择"经验记录"(或 PC 端指定下次录音走复盘模板),按键口述项目复盘:"这次交付延期的根因是…下次应该…" |
| T1 | 与场景一 T4~T6 相同,结构化模板换成"场景/判断/依据/教训/可复用方法" |
| T2 | 生成经验卡片草稿,专家在 PC 端 review 确认 |
| T3 | 归档到该领域的经验库(skill 草稿) |

**D2 存量文档提取**(半自动,MVP 人工触发):

| 时序 | 动作 |
|---|---|
| T0 | 专家/管理员在 PC 端选中文档或邮件,触发"提取经验" |
| T1 | Agent 核心按模板抽取结构化经验,生成经验卡片草稿 |
| T2 | 人工 review、修订、确认 |
| T3 | 入库,沉淀为该领域的专家 skill;后续 Agent 处理同类问题时自动引用 |

**关键设计**:MVP 不追求自动化提取管线,先验证"经验卡片有人产、有人用"。D1/D2 产出**必须经人工确认才能入库**——经验库的错误内容比普通笔记危害大得多。

### 4.5 通用异常(全场景适用)

- **设备未配对/被吊销**:工牌仅显示身份页与"请联系管理员重新配对",录音键无效
- **PC 离线**:录音本地缓存;指令类操作直接提示"电脑不在线,无法执行"
- **连续误触发**:录音 <2 秒视为误触,不上传不提醒,静默丢弃

## 5. 硬件方案

> **v0.2 修订说明**:本章由「单一硬件路径」改为 A/B 两套可独立推进的方案,并直接修正原稿中多处不现实指标:
>
> 1. **「4.2 寸电子纸 + ≤95×60×8 mm」不可同时成立**:4.2 寸裸屏(GDEY042T81)外形约 91×77 mm,屏体宽度已超出整机 60 mm 的目标宽度;能装下该屏的整机至少约 97×83 mm,按真实堆叠厚度约 9.5~10.5 mm(见 5.2.1 / 5.2.3)。
> 2. **「800~1000mAh + 8 mm」基本不可兼得**:8 mm 整机按堆叠只容得下约 3.0 mm 厚电芯(约 500~600mAh);800mAh 以上需要 ≥9.5 mm 厚度(见 5.2.3 组合表)。
> 3. **「16MB Flash 缓存 2 小时 Opus」不成立**:双 OTA 分区 + 中文字库之后仅余约 7MB,16kbps Opus 约 7.2MB/小时,实际只够 ~1 小时(见 5.2.2 重算与两种对策)。
> 4. **「PCB 预留第二麦焊盘」≠ 具备降噪能力**:预留只代表 PCB 兼容,双麦算法与声学结构需单独验证,不进 MVP 承诺(见 5.2.2)。
> 5. **原方案无 NFC**:「后续 NFC 门禁能力」必须显式立项,且「加 PN532/PN7160」不等于能刷企业门禁(见 5.2.4)。
> 6. **开发验证件与量产件严格分开**:开发板/带排针模块只用于阶段 0 验证;EVT/DVT 必须替换为贴片器件 + 定制 PCB。采购链接统一为「淘宝/1688 搜索链接 + 精确型号关键词」——单品链接时效性强且无法逐家核验,具体店铺、价格、起订量一律标**待采购确认**。

#### 5.2.3 A3 录音合规硬件联动与结构设计

**录音 LED 与录音硬件联动的可实现方案**:

- 麦克风电源轨 MIC_VDD 由一颗负载开关(P-MOS 或负载开关 IC)控制,使能信号 REC_EN = GPIO(固件录音使能);
- **录音 LED 的供电直接取自 MIC_VDD**(经限流电阻):麦克风通电 = LED 亮,麦克风断电 = LED 灭,固件无法在录音时单独熄灭 LED,也无法在 LED 灭时悄悄给麦克风供电;
- 物理按键是触发 REC_EN 置位的唯一途径(固件状态机:按键中断 → 录音态;无按键事件不得置 REC_EN);<2 秒录音静默丢弃作为软件兜底;
- 状态关系:REC_EN(硬件使能)→ MIC_VDD 与 LED 同轨 → I2S 时钟由固件在录音态下开启;REC_EN 释放 → MIC_VDD 与 LED 同时掉电 → I2S 时钟关闭。
- **验证方法**:EVT 样机做故障注入——固件强制写 LED 控制脚(应无效,因 LED 无独立控制脚)、示波器/万用表同步量 MIC_VDD 与 LED 电流(应同生同灭)、长时静置 24h 抓 REC_EN 误触发日志。

│ ┌─────────────────────────┐ │
│ │   4.2" 电子纸(身份页)    │ │
│ │                         │ │
│ └─────────────────────────┘ │
└─────────────────────────────┘
  顶侧:录音键(大键程、凸起于壳面、可盲操)
  右侧:确认/返回键(两键,与录音键键程/手感区分)
  底侧:USB-C(配对/调试/充电)+ 挂绳孔
  内部:PCB 居上,天线区在上沿三面净空;电池居中下部;扁平震动马达贴壳

#### 5.2.4 A4 NFC 与门禁边界

- **现状声明**:v0.1 方案**没有 NFC**;「后续 NFC 门禁能力」是新增需求,本节显式立项,硬件仅预留天线区与焊盘,不承诺门禁功能交付时间。
- **必须区分三件事**:

| 能力 | 说明 | 难度 | 前置条件 |
|---|---|---|---|
| ① NFC 标签读取/配对 | 读 NDEF 标签,用于「碰一碰配对/打卡」 | 低 | PN532 级芯片即可,无安全要求 |
| ② 企业门禁凭证 | 工牌被门禁读卡器识别为合法卡 | 高 | 门禁系统类型(13.56MHz MIFARE/DESFire/CPU 卡,还是 125kHz ID 卡)、发卡权限、密钥,缺一不可 |
| ③ 卡模拟 | 工牌模拟一张卡 | 高 | 通常需安全元件(SE/eSE)+ 卡片/门禁厂商授权(如 DESFire 生态) |

**结论修正**:850mAh 在 BLE 优化到位(≤2mA 均值)时满足「5 个工作日」;若 BLE 均值实测 >5mA 则不满足,缓解手段为加大连接间隔/按需连接,**该实测是方案 A 的 Go/No-Go 关键项**。验证方法:阶段 0 用功耗分析仪(PPK2 或同级)连续实测 24h,输出功耗模型校准报告。

#### 5.3.3 B3 门禁与电磁兼容

- **布局红线**:现有工卡必须位于靠近门禁读卡器的一侧(卡套正面);金属壳录音卡、电池、PCB、电子纸背板、磁铁、天线**不得直接覆盖工卡天线区**;刷卡时用卡套正面贴读卡器。
- **先识别卡型**:用支持 NFC 的手机读现有工卡——能读出 = 13.56MHz(MIFARE/DESFire/CPU 卡);读不出且门禁为老式 ID 卡 = 125kHz。两种频率干扰模式不同:13.56MHz 受金属涡流/屏蔽影响大;125kHz 受磁路遮挡影响。**识别责任人:IT/门禁管理员,阶段 0 第一周完成。**
- **「工卡读取距离」逐级验证计划**(每级测 10 次取平均距离与成功率):

| 级别 | 配置 | 目的 |
|---|---|---|
| L0 | 裸卡 | 基线 |
| L1 | 装入空卡套 | 结构本身影响 |
| L2 | +录音卡 | 金属/电路影响 |
| L3 | +电子纸/电池/PCB | 全结构影响 |
| L4 | L3 + Wi-Fi/BLE 发射中 | 射频发射瞬时影响 |

- **不达标补救**(按序尝试):电子模块整体下沿延伸/顶部偏置,远离卡面中心;背面偏置 + 铁氧体隔磁片(13.56MHz,型号待供应商确认);录音卡改选非金属壳款;翻盖/翻转刷卡结构(刷卡时翻开正面层)。
- **红线**:不能因有 NFC 电子纸或 NFC 模块,就声称现有工卡门禁能力自动保留。

| 音频自动进入 PC 伴侣 | Wi-Fi 传输成功率 ≥99%,端到端 ≤60s | 无需人工干预的自动导入(或插拔即自动导入),成功率 ≥99% |

| 录音键/LED/声孔 | 结构评审零遮挡,LED 各角度可见 | 逐项 checklist 零遮挡(以实物测绘开孔图验收) |

| 数据主权 | 音频不进入未经授权的第三方云(架构保证) | 录音卡通过准入 e/f(供应商书面确认) |

#### 5.4.3 推荐推进顺序与结论

1. **不预设方案 B 更易量产**:B 的两个硬前提(录音卡开放接口、门禁抗干扰实测)有一项不过,B 即退化为「纯录音 + 人工导出」的过渡工具,不能进试点。
2. **阶段 0 两线并行(第 1~3 周)**:A 线用开发板验证自研链路(录音/传输/功耗);B 线买录音卡 + 屏模块,做准入核验与 L0~L4 门禁实测。两线共享 PC 伴侣/Agent/协议层,软件不重复投资。
3. **第 3 周末按 §5.4.2 决策**:
   - B 准入全过 → **B 先行试点**(启动快、不动现有门禁发卡),A 继续推进作为量产主线(自主可控、不受录音卡供应商牵制);
   - B 准入任一不过 → **全力 A**,B 仅保留为无集成需求的过渡佩戴验证。
4. **结论**:两方案互不阻塞、互为备份;长期量产以 A 为主线的概率更高(供应链与数据主权可控),B 的价值在于用最低成本提前拿到真实佩戴与使用数据。

### 5.6 结构与合规要点(两方案共用)

- **录音 LED 硬件联动**:实现方案见 5.2.3;验证方法为故障注入 + MIC_VDD/LED 电流同步测量,任何样机阶段不得豁免;
- **数据合规默认项**:原始音频转写后默认删除;设备丢失后 PC 端一键吊销配对;全部操作留审计日志;
- **隐私红线**:两方案均不得有任何形式的自动/声音触发录音(§3.3);方案 B 选用的录音卡若带「声控录音」功能,必须固件/设置层面禁用并写入验收 checklist;
- **开发件与量产件分离**:所有标注「开发验证」的模块不得出现在 EVT 及之后的样机中。

## 7. 关键假设与待决问题

以下问题不阻塞阶段 0 启动,但影响阶段 1 设计,需在 EVT 前给出答案:

1. **办公系统 API 可用性**:任务/日历系统是否开放接口、认证方式如何?决定场景 2/3 的可行边界。
2. **LLM 部署形态**:企业内网大模型 API、PC 本地模型,还是混合?影响 ASR/结构化的时延与数据出域策略。
3. **PC 伴侣的安装权限**:企业 IT 策略是否允许常驻托盘程序?需要提前与 IT 对齐。
4. **录音合规口径**:公司制度对"按键录音 + LED 指示"是否足够,还是被录音方需额外告知?建议法务早介入。
5. **工牌丢失的 HR/IT 流程**:吊销、补办、原设备数据责任的归属流程,试点前需成文。
6. **门禁系统类型与发卡权限**:现有工卡是 13.56MHz 还是 125kHz?是否允许工牌内置/复制门禁凭证?直接决定方案 A 的 NFC 边界与方案 B 的干扰测试方法,详见 §5.5 待确认清单。
