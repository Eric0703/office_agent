# AI 协作开发 — 通用提示词库

> 提炼自「AI 工牌」项目第一轮协作(原始记录见项目根目录 `round1.png` 等过程截图)。
> 用法:按项目阶段选用模板,【】内替换为当前项目内容。核心原则一句话:**把需求转化为可执行规约,再让 AI 按规约施工**。

---

## 阶段一:需求梳理(禁止写代码)

### 1.1 需求文档开场

```
我要开发一个【项目名】项目。现在是需求梳理阶段,禁止写任何代码。

业务场景:【用场景描述,不要直接列功能清单——谁、在什么环境、遇到什么问题、现在怎么解决、为什么不好】

请帮我梳理需求,输出 01-需求文档.md,包含:
1. 功能列表,按"必须做/可以砍/明确不做"三档划分,说明理由
2. 核心用户流程(从用户旅程视角,做出时序描述)
3. 关键选型建议(说明理由,给出否决项的对比)
4. 按阶段的开发路线图,每个阶段写清产出物和验收标准

另外我有一个没想好的问题:【你的疑问】。请你充分考虑业务流的走向,做全面的设计考虑。
```

**为什么有效**:场景描述让 AI 自己做推导而不是复读功能清单;"禁止写代码"锁定阶段边界;三档划分强迫取舍;"没想好的问题"把架构决策权显式交给 AI 并要求论证。

### 1.2 分文档聚焦(某一块是重点时)

```
我发现你的【某文档/某章节】都聚焦在【A 方面】,但【B 方面】才是我关注的重点。
请你再写一份 0X-【B】需求文档.md,作为专门的【B】需求。
```

**为什么有效**:防止重点被稀释在总文档里;子文档可以独立评审、独立迭代。

### 1.3 红线决策的显式声明

```
我的几个决策:
1. 不考虑【某能力】,所有的【某行为】必须是【唯一合法路径】,避免【风险】;
2. 不做【某类功能】,不做成第二个【反面参照物】。
请把这些更新进文档,并检查所有相关章节保持一致。
```

**为什么有效**:否定句红线比正面描述约束力更强;最后一句"检查所有章节"触发 AI 做全局一致性同步,防止决策只落在一处。

## 阶段二:动手前的对齐(关键!)

### 2.1 挑战式澄清(让 AI 论证,而不是顺从)

```
在动手之前,我有几个问题要跟你澄清和讨论:
1. 你的计划是【N 周/某方案】,你觉得我们【实际条件】真的需要吗?
2. 在缺少【关键资源/依赖】的前提下,如何有效地做测试、验证和展示?
3. 你觉得我们应该直接进入【方案 A】吗?还是先【方案 B】?给出你的判断和理由。
```

**为什么有效**:AI 默认倾向给出"标准答案",挑战式提问迫使它按你的实际约束(团队人数、资源、习惯)重新估算和论证。**永远先质疑排期和方案,再批准它。**

### 2.2 规约驱动开发套件(本库最有价值的一条)

```
我认为开发前应该有一套明确的规约,所有人都遵守(包括你):
1. 项目宪法(constitution):不可逾越的原则,写明修改程序——修改必须经我批准;
2. 开发规约(rules):工作流、协议/接口治理、依赖引入规则、测试数据合规、代码规范;
3. 对抗式审查:对已有全部文档做交叉审查,专找自相矛盾、二义表述、不可验收的条款,
   输出审查报告,发现的问题当场修正文档,不允许留到实现时处理;
4. 然后再做开发计划:分解任务卡,每个阶段有明确的验收标准、交付物和验收门(Gate),
   上一阶段未过门不进入下一阶段。

目的:返工可能性最小;后续交接给任何人(或新的 AI 会话)都能快速建立全貌、保持一致。
AI 时代最重要的能力,就是把需求转化为可执行规约。
```

**为什么有效**:宪法解决"AI 自由发挥越界"问题;对抗审查解决"多文档自相矛盾"问题;验收前置解决"做完才发现不对"问题;文档编号体系解决"交接/换会话失忆"问题。

### 2.3 测试数据策略(真实数据难获取时)

```
真实数据恐怕比较困难,有没有方法可以模拟数据?
要求:可以找到公开的、时长合适的语料/数据集作为测试集;合成数据也可以,
但必须带标准答案,能做自动化回归;明确什么入库、什么不入库(合规)。
```

**提炼出的通用三层结构**:合成集(机器生成、带标准答案、主力回归)/ 公开集(真实分布、许可合规、质量抽检)/ 基线集(标准指标、横向对比)。

## 阶段三:架构设计

### 3.1 汇报用架构产物(给非技术听众)

```
我需要一个可以拿出去讲解的架构产物,给领导汇报用。不用几万字的详细设计,
但至少:用户旅程、输入→处理→输出、技术栈写明白,配架构图(Mermaid,可直接截图进 PPT),
让所有人看得到这个项目是有正规架构设计的规范运作项目。
```

### 3.2 工程设计四件套(给开发者/AI 自己施工用)

```
架构设计我想看到:状态图(Mermaid)、模块划分(职责/接口/依赖方向)、
数据表设计(字段到类型级,写明关键约束)、项目目录结构规划。
针对缺失的部分,请你补齐。
```

**为什么有效**:四件套恰好覆盖"系统有哪些状态、谁干什么、数据长什么样、代码放哪"——AI 施工时不会自己发明第二套结构。

## 贯穿全程的工作方式

### 4.1 顺序原则(先做什么,后做什么)

1. **阶段 0 永远是需求与规约**,禁止代码;
2. **先钉住改起来最贵的东西**(协议、模块边界、数据模型),再让原型在UI层裸奔;
3. **验收标准前置**,写计划时先写验收门,再写任务;
4. **文档即事实**:改行为先改文档,文档与实现同次变更;
5. 每轮决策修正后,**检查全部文档一致性**(对抗审查机制化)。

### 4.2 什么是必须的(Must)

- 每个功能需求带**可验证的验收标准**(数字、可观察行为,不要"体验良好"这种话);
- 每个阶段有**交付物清单**和**退出条件**;
- 风险操作有**确认回路**,全量操作有**审计日志**;
- 外部依赖全部走**适配层/抽象接口**,永远可 Mock;
- 选型必须写**理由 + 否决项对比**,不允许"业界主流"四个字糊弄。

### 4.3 什么是禁止的(红线模板)

- 禁止无任务卡的编码、超出任务范围的"顺手重构";
- 禁止引入未批准的第三方依赖;
- 禁止"先改代码后补文档";
- 项目特定红线(如本项目的:无感录音、端侧智能、通用通知推送)——用否定句写进宪法。

### 4.4 过程记录(本项目实践)

- 每轮关键对话的原始提示词截图存档(如 `round1.png`),阶段结束后提炼进本库;
- 好提示词的判断标准:**AI 的输出可以直接成为交付物,且无需返工对齐**;
- 失效或过时的模板及时删除,本库保持"每条都可直接复制使用"。
